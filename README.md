# Automated Fault Detection for Distributed Checkpointing

## 1. About the Project

This repository implements a rigorous, multi-process validation harness designed to catch subtle, silent checkpoint-resume bugs in distributed training pipelines (e.g., PyTorch DistributedDataParallel). It provides a formal **State Contract Registry** to explicitly define and validate the invariants of model, optimizer, scheduler, dataloader, and RNG states across all processes before training resumes.

## 2. Scenario and Background

A typical training pipeline maintains distributed state across multiple ranks, such as model weights, optimizer momentum, learning rate schedulers, and often an exponential-moving-average (EMA) "teacher" copy of a student model. In large-scale distributed setups, training is routinely interrupted and resumed from checkpoints. 

Ideally, the restored state should exactly match the uninterrupted state across all ranks. However, seemingly innocuous implementation details—such as relying on a scalar variable inside a distributed process—can lead to state drift between ranks if the data isn't synchronized correctly upon restoration.

## 3. About the Bug

Distributed models often resume training smoothly from checkpoints but silently suffer from state desynchronization across ranks. For instance:

- **EMA Scalar Omission**: A scalar `step` tracker used to calculate EMA decay rate is stored as a plain Python `int` rather than a registered tensor buffer. Upon restoration, only rank 0 successfully re-applies the scalar, leaving all other ranks with a stale value.
- **Data Cursor Mismatches**: Dataloaders increment out of sync when the `global_step` is improperly restored, causing ranks to process completely different global batches.
- **RNG Desynchronization**: Random number generator seeds diverge because the global RNG state is not properly synchronized across the distributed cluster.

These bugs are virtually invisible in single-rank loss curves, but cause the distributed shards to silently drift apart. Over time, this leads to diverging model weights, degraded accuracy, or sudden training instability that is notoriously difficult to debug.

## 4. Test Results

The harness includes an automated fault injection matrix that proves the effectiveness of the validation system. It modifies checkpoints offline to simulate the bugs and forces the pipeline to restore them.

**End-to-End Recovery Fidelity**
When a checkpoint is successfully saved and resumed without faults, the pipeline mathematically guarantees an identical recovery, matching the continuous baseline loss perfectly:

## 5. Real Life Use Case

In production environments, training large language models (LLMs) or massive vision models occurs across hundreds of GPUs over several weeks. Hardware failures are common, and cluster preemptions force training to pause and resume frequently.

If a silent state desynchronization bug occurs during a resume cycle, the training run may proceed for days before researchers realize the model has irrecoverably diverged. This validation harness acts as a critical safety net, executing a fast, cross-rank structural and tensor-level verification check at the exact moment of restoration. If any state dimension (e.g., RNG, optimizer, EMA) has drifted across nodes, the training run safely halts before consuming thousands of dollars of wasted compute.

## 6. The Structure

```
├── configs/benchmarks/    # YAML configurations for ResNet and Transformer workloads
├── scripts/               # Bash scripts for running fault matrices and benchmarks
├── src/
│   ├── checkpoint/        # Torch checkpoint backend and distributed manifest handling
│   ├── experiments/       # Entrypoints for baseline runs, faults, and resumes
│   ├── faults/            # Fault injection scripts (e.g. rng.py, scheduler.py)
│   ├── runtime/           # Process group initialization (Gloo/NCCL) and seed setups
│   ├── validator/         # The core cross-rank state validation engine
│   └── workloads/         # Implementations of ResNet and Transformer pipelines
└── results/               # Directory for generated metrics, logs, and paper tables
```

## 7. Setup and Usage

The project utilizes `uv` for lightning-fast Python dependency management.

```bash
uv sync
```

The project provides three primary bash scripts to run the test suite and extract results. All scripts are executed using `torchrun` in a multi-process environment.

### Run the Fault Injection Matrix
Runs the baseline for all workloads, mutates the checkpoints with simulated bugs, and attempts restoration to ensure the validation harness triggers.
```bash
./scripts/run_fault_matrix.sh
```

### Measure Validation Overhead
Runs the workloads with validation disabled, then enabled, computing the exact wall-clock overhead introduced by cross-rank tensor comparisons.
```bash
./scripts/run_benchmarks.sh
```

### Generate Evaluation Tables
Automatically parses the raw JSON logs outputted by the matrices and generates Markdown tables for research papers.
```bash
./scripts/generate_paper_tables.sh
```
